# Polycards

A vocabulary spaced-repetition (SRS) web app for Japanese junior high and high school students learning English. Think WaniKani or Anki, built for my classes at Ryukoku Junior/Senior High School. I'm an English teacher, not a professional developer, so explain changes in plain language.

## Stack
- React + Vite. Code layout:
  - `src/App.jsx`: shared state (session, screen, My Cards data) and which screen to show
  - `src/components/`: one file per screen part (`StudySession`, `MyCardsTab`, `MasteredList`, `StarIcon`, `CardSetsTab`, `CardSetsHub`, `NavRow`, `LevelSwitch`, `LoginScreen`, `Header`, `Tabs`, `Stamp`, `PlayerStats`, `LevelChart`, `ReviewPlanSheet`, `Avatar`, `AvatarPicture`, `FlipCard`, `WordInfo`, `WordList`, `Highlighted`, `AddDeckButton`, `GachaScreen`, `GachaReveal`, `GachaCollection`, `GachaMachine`, `GachaIcons`, `ToggleSwitch`)
  - `src/lib/srs.js`: SRS rules, plus `srsAnswer()` (what one review answer sends and shows) `newSessionId()` and `saveErrorReporter()`; `src/lib/spelling.js`: typing-mode spelling check (a copy of `spelling_check()` in the SQL), the other-meaning retry rule and the typing-mode setting (pure functions); `src/lib/points.js`: points and rank (pure functions); `src/lib/drill.js`: building/shuffling card piles; `src/lib/dictionary.js`: builds the dictionary link for a word; `src/lib/library.js`: shapes the Card Sets library and its back-button rules (pure functions); `src/lib/schedule.js`: next-review wording and the review plan, in Japan time (pure functions); `src/lib/sheet.js`: when a pop-up closes; `src/lib/gacha.js`: rarity labels/colors, ticket progress, collection grouping, and `singleFlight()` for the pull button (pure functions); `src/lib/api.js`: every Supabase query (and `recordAnswer`, the only way review answers are saved); `src/lib/supabaseClient.js`: creates the Supabase client
  - `src/styles/theme.js`: shared colors (as CSS variables), fonts, and button styles
  - `src/themes.js`: color themes (values for each color role) and `applyTheme()`
- Supabase: PostgreSQL, Auth, Row Level Security
- Sign-in: Google OAuth, open to any Google account. Signing in is required; the old "Skip login (Test App)" bypass has been removed. Email/password is enabled in Supabase but has no sign-in screen in the app.
- Deployed on Vercel at https://polycards-eight.vercel.app. Vercel redeploys automatically on every push to `main`, so a push to `main` goes live. For now the live site is for teacher testing only; students don't have access yet.

## Database (Supabase)
Library tables (read-only for everyone, I add content myself in the Supabase SQL editor):
- `textbooks` (id, name, school_level: `JHS` | `HS` | `Other`)
- `units` (id, textbook_id, name, unit_order)
- `decks` (id, unit_id, name)
- `words` (id uuid, english, japanese, example_en, example_ja): one shared word list; a word can appear in several decks. `example_en` / `example_ja` are optional example sentences (some words don't have them yet)
- `deck_words` (deck_id, word_id, position): which words are in which deck
- Word ids are **uuids, not numbers**: `words.id` and every `word_id` (`deck_words`, `user_cards`, `counted_cards`, `answer_log`, and `record_answer`'s `p_word_id`). `supabase/polycards-fix-word-id.sql` (2026-10-16) changed `counted_cards.word_id`, `answer_log.word_id` and `record_answer` from bigint to uuid (that bug made every review save fail with 保存できませんでした and stopped the gacha review counter); `polycards-gacha.sql` and `polycards-answers.sql` are updated to match.
- `cards` is the OLD per-deck word table. It still exists but must not be used.

Per-student tables (RLS: each user can only touch their own rows; `user_id` defaults to `auth.uid()`):
- `user_decks` (user_id, deck_id, added_at): decks added to My Cards
- `user_cards` (user_id, word_id, direction, level, next_review_at, mastered_at, updated_at): progress per word AND direction, primary key (user_id, word_id, direction). Level 8 = Mastered: `next_review_at` is NULL and `mastered_at` is when it was mastered (NULL for every other level). CHECK constraint `user_cards_level_range` allows level 0 to 8. Progress belongs to the word, not the deck, so a shared word has one level across all of a student's decks.
- `user_stats` (user_id primary key default `auth.uid()`, peak_points, updated_at): highest points the student has ever had. RLS own row only; the trigger `user_stats_keep_peak` keeps `peak_points` at the highest value ever saved.

Gacha tables (created by `supabase/polycards-gacha.sql`; students may only SELECT, and only some of them):
- `avatars` (id, slug, name_ja, name_en, rarity: `normal` | `rare` | `super_rare` | `secret`, series, image_url (NULL = placeholder picture), is_starter, active, sort_order): no direct access for students, so Secret names stay hidden.
- `user_avatars` (user_id, avatar_id, obtained_at): who owns which avatar.
- `user_gacha` (user_id, reviews_counted, tickets_spent, pulls_since_secret, equipped_avatar_id, theme): one row per student.
- `counted_cards` (user_id, word_id, direction, last_counted_at): which cards were counted as a review (functions only).
- `theme_unlocks` (theme_key, unlock_level): `unlock_level` is the rank needed.
- Reviews are counted by the trigger `user_cards_count_review` on `user_cards` (a due card whose schedule changes = one review; the same card at most once per 3 hours). Tickets: 1 after the first review, +1 per 100 reviews, +1 every 10th rank, minus tickets used. Settings live in `gacha_setting()`.

Gacha functions. **The app only calls these RPCs (`supabase.rpc`, in `src/lib/api.js`); it never reads or writes the gacha tables directly and never counts reviews or tickets itself.**
- `gacha_status()` → `{ tickets, reviews_counted, reviews_to_next_ticket, reviews_per_ticket, remaining, owned, total, odds: { normal, rare, super_rare, secret } (percent, live: from the rarities the student still lacks), player_level (= the rank), equipped_avatar: { id, slug, name_ja, name_en, rarity, image_url }, theme }` (`fetchGachaStatus`)
- `gacha_pull()` → `{ avatar: { id, slug, name_ja, name_en, rarity, series, image_url }, tickets_left }`; always an avatar the student doesn't have; locks the student's row so two taps can't spend one ticket twice (`pullGacha`)
- `gacha_collection()` → rows `{ id, slug, rarity, series, sort_order, owned, obtained_at, equipped, name_ja, name_en, image_url }`; unowned rows have no slug/name, unowned Secrets also no picture (`fetchGachaCollection`)
- `gacha_equip_avatar(p_avatar_id)` (`equipAvatar`), `gacha_set_theme(p_theme)` (`setGachaTheme`, not used by the screens yet)
- Error codes → messages (`gachaErrorMessage()`): `no_tickets` ガチャ券がありません, `collection_complete` 全部そろいました！新しいアバターをお楽しみに, `not_owned` このアバターはまだ持っていません, `theme_locked` このテーマはまだ使えません, `not_signed_in` ログインしてください.

Answer log and study stats (created by `supabase/polycards-answers.sql`, run after the gacha SQL; students may only SELECT their own rows, only `record_answer()` writes them):
- `answer_log` (id, user_id, session_id, word_id, direction, result: `got_it` | `not_yet` | `dont_know`, is_repeat, typed, typed_answer, spelling: `exact` | `close` | `wrong`, level_before, level_after, bonus_points, answered_at): one row per answer in a review.
- `user_study_daily` (user_id, day (Japan date), reviews, got_it, not_yet, dont_know, repeats, typed, spelled_correctly, bonus_points): totals per student per day. `reviews` = first answers only; repeats are counted separately.
- `user_study_totals` (user_id, same counters, updated_at): all-time totals. `bonus_points` (spelling bonus) now counts toward rank: `gacha_player_level()` = `floor(sqrt((peak + bonus) / 20)) + 1`.
- Settings in `study_setting()` (spelling bonus, answer_log cleanup, which is built but OFF). Spelling check functions (`spelling_normalize`, `spelling_distance`, `spelling_check`) are used by typing mode; **`src/lib/spelling.js` must give the same results as them** (the app's copy only shows ✓ / おしい instantly; the database decides the bonus).

`record_answer(p_word_id uuid, p_direction text, p_result text, p_session_id uuid, p_typed text default null)` → `{ result, is_repeat, level_before, level_after, mastered, spelling, bonus_points, bonus_total }`. It works out the new level itself (same rules as `src/lib/srs.js`), saves the `user_cards` row, logs the answer and adds to the daily/total stats; the gacha review counter trigger still runs. `p_result`: `got_it` (わかった), `not_yet` (まだ), `dont_know` (わからない, not used yet). An answer is a repeat when the same card was already answered with the same session id; a repeat わかった is logged but changes no level. Errors: `not_signed_in`, `bad_answer`, `card_not_found`, `not_due` (a first answer on a card that isn't due).
- **Review answers are saved only through `record_answer`**: `recordAnswer(card, result, sessionId)` in `src/lib/api.js`. The app never writes `user_cards` levels after an answer. Answers are sent one at a time, in the order they were given (a queue: each waits for the previous one; a failed one doesn't block the next), and each is tracked in `pendingSaves` so `waitForPendingSaves()` still holds points/tickets until saves finish. Errors: `not_due` → only `console.warn`; `card_not_found` → このカードは見つかりませんでした; `not_signed_in` → ログインしてください; anything else → 保存できませんでした (`answerErrorMessage()`). Every failure is logged with `console.error`, but the pop-up shows at most once per review session (`saveErrorReporter()` in srs.js, one per `StudySession`).
- `StudySession` makes one session id per review (`newSessionId()` in srs.js: `crypto.randomUUID()`, with a hand-built UUID v4 fallback for older browsers / plain-http addresses) and calls `recordAnswer` for every SRS answer (わかった → `got_it`, まだ → `not_yet`), including わかった on a card missed earlier. The Card Sets drill writes nothing.
- Tests: `src/lib/api.test.js` (arguments, order, errors, no `user_cards` write), `StudySession.test.jsx` (`srsAnswer`, `newSessionId`, `saveErrorReporter`).

`other_meaning_check(p_word_id uuid, p_typed text)` → boolean (from `supabase/polycards-other-meaning.sql`): true when what was typed is exactly another library word that shares a Japanese meaning with this card (e.g. "from" on the から card that wants "since"). Saves nothing. Called only by `checkOtherMeaning(wordId, typed)` in `src/lib/api.js`, which never throws: an error → `console.warn` and false.

Shared-word rules:
- Adding a deck creates `user_cards` rows for each of its words in both directions and skips words the student already has, so existing progress is kept.
- Removing a deck deletes progress only for words that are not in any of the student's other added decks.
- Per-deck due counts count a shared word under every added deck that contains it, so per-deck numbers can add up to more than the "Due now" total.

Rules:
- Never change the schema or RLS yourself. Write the SQL in a separate block and I will run it in the Supabase SQL editor.
- Never commit secrets. The anon key is public by design, but a service-role key must never appear in the repo.
- Supabase returns at most 1,000 rows per query; keep that in mind for large lists.

## SRS rules (constants and level logic in `src/lib/srs.js`)
- Levels 0 to 7. Wait before a card is due again, by the level it just reached: `LEVEL_HOURS = [0, 4, 24, 72, 168, 336, 720, 2880]` (new, 4h, 1d, 3d, 1w, 2w, 30d, ~4 months).
- Correct on the first try: level +1. Correct at level 7 = **Mastered** (`MASTERED = 8`, `isMastered()`): never scheduled again, left out of due counts and reviews (`.lt('level', MASTERED)` in `fetchDueRows` / `fetchReviewRows`). A miss at level 7 drops as usual. Mastery is per card (per direction).
- The database works out and saves the level after an answer (`record_answer`), so **`LEVEL_HOURS` and the miss penalty (`levelAfterWrong`) in srs.js must stay in step with `study_level_hours()` and `record_answer` in `supabase/polycards-answers.sql`**. The app still uses `levelAfterCorrect` / `levelUpLabel` for the level-up float. Putting a card back (not an answer) is still written by the app with `restoreUpdate()`: `RESTORED_LEVEL = 1`, due now, `mastered_at` NULL.
- Wrong answers (WaniKani style): the drop is based on how many times the card was missed this session, rounded up in pairs. The 1st and 2nd miss = 1 level down, the 3rd and 4th = 2 levels down, and so on (the first miss already costs a level). From level 5 up the penalty is doubled (1st/2nd miss = 2 levels down). A learned card never drops below level 1; a new card (level 0) stays at 0. The drop is always counted from the level the card had at the start of the session, and the lowered level is saved at each miss.
- A card missed in a session comes back later that session as extra practice. It does not move up again that session.
- Review sessions are capped at `SESSION_SIZE = 20` cards.
- These rules are covered by automated tests in `src/lib/srs.test.js` (and drill helpers in `src/lib/drill.test.js`). Run them with `npm test`. If a rule is changed on purpose, update its test in the same change.

## Points and rank
- Each card (one `user_cards` row, so both directions count separately) is worth `CARD_POINTS = [0, 1, 2, 3, 5, 8, 13, 21, 34]` by level (the last entry is Mastered) (in `src/lib/srs.js`, next to `LEVEL_HOURS`). Level 0 cards are worth 0, so adding a deck gives no points until cards are learned.
- Current points = sum over all of the student's `user_cards`. Peak points = highest ever, saved in `user_stats`.
- The player's level is called **Rank** (so it isn't confused with card levels Lv0 to Lv7). The database still calls it `player_level` (`gacha_player_level()` and the `player_level` field of `gacha_status()`); the app treats it as the rank.
- Rank comes from **peak points + spelling bonus points** via `playerRank(peak + bonus)` in `src/lib/points.js` (the only place the formula lives in the app): `floor(sqrt((peak + bonus) / 20)) + 1`, the same as `gacha_player_level()` in the database. The bonus is `user_study_totals.bonus_points` (`fetchBonusPoints()`, own row, `maybeSingle`, 0 if none; loaded with the peak in `loadStats`, and a failed load counts as 0). The saved peak is card points only. Rank 2 at 20 points, Rank 3 at 80, Rank 4 at 180, Rank 10 at 1,620.
- Rank never goes down: removing a deck lowers current points but not the peak.
- Points are recounted each time the dashboard is shown (so after every review), after pending progress saves finish. If the total beats the saved peak, the new peak is upserted to `user_stats`.
- All card levels are read in pages of 1,000 (`fetchAllCardLevels` in `src/lib/api.js`; `fetchDueRows` is paged the same way), so totals are correct beyond Supabase's 1,000-row limit.
- Shown at the top of My Cards by `src/components/PlayerStats.jsx` (avatar, rank labeled ランク and shown as "Rank N", current and peak points, and a bar showing progress to the next rank, "あと N pt → Rank N+1"). The bar uses `pointsForRank()` in `src/lib/points.js`, the reverse of `playerRank()`, and is measured from peak + bonus because the rank comes from them. Sizes are in `wideLayout` in theme.js: column up to 1100 px with 32 px padding; My Cards in two columns (440 px: player card, review button, level chart, Mastered | マイデッキ rows in a 2-column grid); study 780 px wide with a taller card, bigger text (answer 48 px, question 30 px, example 24 / 18 px) and 76 px answer buttons; other screens (Card Sets, word list, Mastered, login) centered at 720 px. - Gacha button (`GachaButton` in `Header.jsx`, left of the account button, same 44 px round style, capsule icon from `GachaIcons.jsx`): no tickets = `accent` outline and icon; tickets waiting = `gold` outline and icon plus a small `danger` badge with the count. When the app opens with tickets waiting it pulses once (class `gacha-pulse`, 1.4 s, off with reduce motion). Tapping it opens the gacha screen.
- `Tabs.jsx` is a bottom tab bar fixed to the screen (72 px, `tabBarHeight`), shown on the dashboard only; the dashboard has extra bottom padding so nothing hides behind it.
- Avatar pictures: always use `AvatarPicture.jsx` (`avatar`, `size`, `silhouette`), used by PlayerStats (the equipped avatar from `gacha_status`), the reveal and the collection. `image_url` set → the image; slug `cat` (or no avatar yet) → `Avatar.jsx`, the low-poly cat in `danger` shades; anything else → a generic low-poly blob tinted by rarity with the first letter of `name_en`. The account button keeps the initial letter. Picture uploads come later.
- Next review (次の復習): when nothing is due, the gray review button shows a second line like 次の復習：2時間後に 7枚 (`nextReviewSummary()` in `src/lib/schedule.js`). The time is the earliest future `next_review_at` (Mastered never counts); the number is how many cards come due in that same Japan-time clock hour (`fetchNextReview()`: one query for the earliest time, one count-only query). Wording rounds up: under 1 hour 45分後, under 24 hours 2時間後, otherwise 10月15日. No line when the student has no cards or only Mastered ones. If the review is today or tomorrow, the button is tappable (›) and opens the review plan; after tomorrow it stays disabled.
- Review plan pop-up (`ReviewPlanSheet.jsx`): bottom sheet on phones, centered box from 600 px (classes `review-plan-backdrop` / `review-plan-sheet` in `src/index.css`). 今日 (now until midnight) and 明日 (all of tomorrow), one row per hour with cards (18:00　7枚) and a 合計 per day, or 今日はもう復習はありません / 明日の復習はありません. "Today", "tomorrow" and hours are always Japan time (UTC + 9, no daylight saving), whatever the device timezone. Rows come from `fetchReviewPlanRows()` (paged, loaded each time it opens), grouped by `groupReviewPlan()`. Closes with ×, Escape or a tap on the backdrop (`shouldCloseSheet()`). Tests: `src/lib/schedule.test.js`, `src/lib/sheet.test.js`, `ReviewPlanSheet.test.jsx`, `MyCardsTab.test.jsx`.
- Refresh: on the dashboard, due cards and the next review reload whenever the app comes back into view (`visibilitychange`). While nothing is due, a 60-second timer keeps the wording current and reloads once the next review time has passed, so 復習を始める can appear up to about a minute late.
- New cards (level 0) get `next_review_at = now()` from the database default when a deck is added, so they are due right away.
- Interface is mostly Japanese. Keep the "English to Japanese" / "Japanese to English" direction labels in English. Answer buttons are bilingual (English plus Japanese). Do not add furigana unless I ask.
- Use American English spelling in anything written in English for school or work.
- Inline styles in each component. Colors, fonts and button styles come from `src/styles/theme.js`. Never write hex codes, `rgb()` or color names in `src/App.jsx` or `src/components/`; a test fails if you do.
- Themes: every color is a named role (`bg, surface, surface2, line, text, muted, accent, accentInk, accentText, danger, dangerInk, gold`) plus 8 level colors (`colors.level(n)`, Lv0 to Lv7). `colors.x` in theme.js is `var(--x)`; `applyTheme()` in `src/themes.js` fills in the variables on `<html>` (called in `src/main.jsx`). Themes: `midnight` "Midnight Arcade" (default, dark), `pizza` and `lagoon` (defined, not yet offered to students; planned as rank unlocks, saving the choice will need SQL).
- `accent` is for fills only (buttons, active tab, stamps), never text: lagoon's accent is too light to read as text. When text should look like the accent (the rank "Rank 3"), use `accentText`: the same color as `accent` in midnight and pizza, a darker coral in lagoon so it passes contrast. Points and other big numbers use `gold`, headings and links use `text`/`muted`, "Still learning" uses `btnDanger`.
- `src/themes.test.js` checks that every theme has every role and that text passes WCAG 4.5:1 contrast. A new theme must pass it.
- Trying a theme: only under `npm run dev`, add `?theme=pizza` or `?theme=lagoon` to the URL. Ignored on the live site (temporary until the unlock feature).
- Fonts (Google Fonts, loaded in `index.html`): Chakra Petch for headings and numbers (`fontDisplay`), Zen Maru Gothic for body and Japanese (`fontBody`).

## How to work with me
- Make small, focused changes. Before large refactors (like reorganizing folders or moving logic between many files), propose a plan and wait for approval.
- After a change, run `npm test`, `npm run lint` and `npm run build`, then summarize in a few plain sentences what changed and how I can test it.
- If you are not certain a step or command is correct, say so instead of guessing.
- Work on a branch, not on `main`. Suggest a git commit message after each working change.
- Never push to `main` (or merge into it) unless I say so, because that deploys to students. Don't push other branches unless I ask.
