# Polycards

A vocabulary spaced-repetition (SRS) web app for Japanese junior high and high school students learning English. Think WaniKani or Anki, built for my classes at Ryukoku Junior/Senior High School. I'm an English teacher, not a professional developer, so explain changes in plain language.

## Stack

## Database (Supabase)
Library tables (read-only for everyone, I add content myself in the Supabase SQL editor):
- `textbooks` (id, name, school_level: `JHS` | `HS` | `Other`)
- `units` (id, textbook_id, name, unit_order)
- `decks` (id, unit_id, name)
- `words` (id uuid, english, japanese, example_en, example_ja, alt_answers): one shared word list; a word can appear in several decks. `example_en` / `example_ja` are optional example sentences (some words don't have them yet). `alt_answers text[] not null default '{}'` = other English answers also accepted in typing / handwriting (see Alternate answers below; added by `supabase/polycards-alt-answers.sql`). Recorded audio (`supabase/polycards-word-audio.sql`, which must be run before deploying app code that selects `audio_path`): `speak_as` (record this text instead of the English, e.g. 'How old are you?'), `audio_path` (file in the `word-audio` bucket), `audio_text` (exact text recorded), `audio_voice` (voice used); the last three are written only by `npm run audio`. `pos` (text, nullable, CHECK = one of noun, verb, adjective, adverb, preposition, pronoun, conjunction, auxiliary, article, interjection, number, phrase) = the word's part of speech (品詞), NULL = none yet (no chip). Added by `supabase/polycards-pos.sql`, **which must be run before deploying app code that selects `pos`**. To fill one in: `update public.words set pos = 'noun' where english = 'dog';` `reading` (text, nullable) = the `japanese` text with kanji and katakana written in hiragana (punctuation, ～, brackets and numbers kept in the same places; katakana is always stored as hiragana), for kana search in the future dictionary; NULL = not filled in yet. Added by `supabase/polycards-word-readings.sql` (no grant change needed: the whole table is readable). **The app does not select it yet**; only the import tool fills it in. `supabase/check-word-readings.sql` (read-only) lists the words still missing one.
- `deck_words` (deck_id, word_id, position): which words are in which deck
- `collections` (id, name, parent_id, sort_order): the Tests & Themes tree, up to 4 levels deep (top level = `parent_id` null). `collection_decks` (collection_id, deck_id) links decks to collections; those decks have `unit_id` null. First real one: 小学校の英語 (40 decks, "1 あいさつ" … "40 疑問詞", imported with the Deck Import Tool SQL).
- Word ids are **uuids, not numbers**: `words.id` and every `word_id` (`deck_words`, `user_cards`, `counted_cards`, `answer_log`, and `record_answer`'s `p_word_id`). `supabase/polycards-fix-word-id.sql` (2026-10-16) changed `counted_cards.word_id`, `answer_log.word_id` and `record_answer` from bigint to uuid (that bug made every review save fail with 保存できませんでした and stopped the gacha review counter); `polycards-gacha.sql` and `polycards-answers.sql` are updated to match.
- `cards` is the OLD per-deck word table. It still exists but must not be used.

Per-student tables (RLS: each user can only touch their own rows; `user_id` defaults to `auth.uid()`):
- `user_decks` (user_id, deck_id, added_at): decks added to My Cards
- `user_cards` (user_id, word_id, direction, level, next_review_at, mastered_at, updated_at): progress per word AND direction, primary key (user_id, word_id, direction). Level 8 = Mastered: `next_review_at` is NULL and `mastered_at` is when it was mastered (NULL for every other level). CHECK constraint `user_cards_level_range` allows level 0 to 8. Progress belongs to the word, not the deck, so a shared word has one level across all of a student's decks.
- `user_cards` RLS: one policy, "Users manage own card progress" (ALL, own rows), recorded in `supabase/polycards-user-cards-policies.sql` (created in the dashboard). It lets a student write any level directly, not only through `record_answer`.
- `user_training_progress` (user_id, practice_id, first_completed_at, last_completed_at, times_completed): Training tab progress (see Training tab).
- `user_stats` (user_id primary key default `auth.uid()`, peak_points, updated_at): highest points the student has ever had. RLS own row only; the trigger `user_stats_keep_peak` keeps `peak_points` at the highest value ever saved.

Gacha tables (created by `supabase/polycards-gacha.sql`; students may only SELECT, and only some of them):
- `avatars` (id, slug, name_ja, name_en, rarity: `normal` | `rare` | `super_rare` | `secret`, series, image_url (NULL = placeholder picture), is_starter, active, sort_order): no direct access for students, so Secret names stay hidden.
- `user_avatars` (user_id, avatar_id, obtained_at): who owns which avatar.
- `user_gacha` (user_id, reviews_counted, tickets_spent, pulls_since_secret, equipped_avatar_id, theme): one row per student.
- `counted_cards` (user_id, word_id, direction, last_counted_at): which cards were counted as a review (functions only).
- `theme_unlocks` (theme_key, unlock_level): `unlock_level` is the rank needed.
- `user_gacha.seen_theme_unlocks` (text[]): unlock pop-ups the student has seen (`seen_theme_unlocks()` / `mark_theme_unlocks_seen()`, see Settings, themes and unlocks).
- Reviews are counted by the trigger `user_cards_count_review` on `user_cards` (a due card whose schedule changes = one review; the same card at most once per 3 hours). Tickets: 1 after the first review, +1 per 100 reviews (review tickets capped at 1 per day, `supabase/polycards-ticket-daily-cap.sql`), +1 every 10th rank, +1 per 150 spelling bonus points (all-time, no daily cap, `gacha_setting('spelling_points_per_ticket')`, `supabase/polycards-spelling-tickets.sql`), minus tickets used. Settings live in `gacha_setting()`. Teacher gift tickets: `supabase/polycards-gift-tickets.sql`.

Gacha functions. **The app only calls these RPCs (`supabase.rpc`, in `src/lib/api.js`); it never reads or writes the gacha tables directly and never counts reviews or tickets itself.** One exception: `theme_unlocks` is read directly (`fetchThemeUnlocks`, once after sign-in), because the unlock ranks are needed for the theme picker.
- `gacha_status()` → `{ tickets, reviews_counted, reviews_to_next_ticket, reviews_per_ticket, next_ticket_tomorrow (true = today's review ticket is already earned), spelling_points, spelling_points_per_ticket (150), spelling_to_next_ticket (1–150), remaining, owned, total, odds: { normal, rare, super_rare, secret } (percent, live: from the rarities the student still lacks), player_level (= the rank), equipped_avatar: { id, slug, name_ja, name_en, rarity, image_url }, theme }` (`fetchGachaStatus`)
- `gacha_pull()` → `{ avatar: { id, slug, name_ja, name_en, rarity, series, image_url }, tickets_left }`; always an avatar the student doesn't have; locks the student's row so two taps can't spend one ticket twice (`pullGacha`)
- `gacha_collection()` → rows `{ id, slug, rarity, series, sort_order, owned, obtained_at, equipped, name_ja, name_en, image_url }`; unowned rows have no slug/name, unowned Secrets also no picture (`fetchGachaCollection`)
- `gacha_equip_avatar(p_avatar_id)` (`equipAvatar`), `gacha_set_theme(p_theme)` (`setGachaTheme`, used by the theme picker and the unlock pop-up)
- Error codes → messages (`gachaErrorMessage()`): `no_tickets` ガチャ券がありません, `collection_complete` 全部そろいました！新しいポリアバターをお楽しみに, `not_owned` このポリアバターはまだ持っていません, `theme_locked` このテーマはまだ使えません, `not_signed_in` ログインしてください.

Teachers and classes (created by `supabase/polycards-teachers.sql`, 2026-10-30; must be run before deploying app code that calls these functions). **Security is in the database, not the UI**: hiding the 先生 tab is only convenience.
- `teachers` (user_id, added_at): who is a teacher. RLS on, no policies, no grants: only the SQL editor can read or change it (the snippet to add one, by username or email, is at the top of the SQL file). `is_teacher()` (SECURITY DEFINER, stable) is how policies and the app ask; `user_is_teacher(uuid)` is internal.
- `classes` (id uuid, name, school_year int (年度), join_code (6 chars from `ABCDEFGHJKMNPQRSTUVWXYZ23456789`: no 0/O, 1/I/L; unique), archived, created_by, created_at), `class_teachers` (class_id, teacher_id: co-teachers; the creator is added by `create_class`), `class_members` (class_id, student_id, real_name, student_number 1–99 or null, joined_at; a student may be in several classes).
- All three: RLS on, **read-only** (`grant select` + policies; no insert/update/delete grants: every change goes through the functions). Teachers read only classes they teach (`is_teacher_of_class(id)`); a student reads only their **own** `class_members` rows and never a `classes` row (so never a join code). Helpers for policies and later phases: `is_teacher_of_class(class_id)`, `is_teacher_of_student(student_id)` (any class I teach, archived included), all SECURITY DEFINER so policies never recurse. A teacher removed from `teachers` loses access to every class at once.
- Teacher RPCs (each raises `not_signed_in`, `not_teacher` or `not_class_teacher` first): `create_class(name, year)` → `{ id, join_code }`, `update_class`, `set_class_archived`, `regenerate_join_code` → new code, `teacher_classes(p_archived)` (with `student_count`), `class_detail(class_id)` → `{ class, students (with display_name / email from auth.users), teachers (is_me) }`, `search_users(query, teachers_only)` (username / Google name / email, partial, any case, `%` `_` literal, 2+ chars, max 20; returns id, display_name, username, email, is_teacher), `add_student_to_class`, `update_class_member`, `remove_student_from_class`, `add_co_teacher` (target must be a teacher). Student RPCs: `check_join_code(code)` → `{ id, name }`, `join_class(code, real_name, number)` (rejects `bad_code`, `class_archived`, `already_member`), `my_classes()` (names only, not archived). Other error codes: `bad_name`, `bad_number`, `bad_class_name`, `bad_school_year`, `query_too_short`, `user_not_found`, `target_not_teacher`, `already_teacher`, `not_member` → messages via `classErrorMessage()` in api.js (`CLASS_ERRORS`). Display names: `user_display_name()` = username, else full_name, else name, else email (the same order as `accountName()`; there is no profiles table).

## Deck Import Tool
- `tools/deck-import-tool.html`: open the file in a browser (not part of the app or the build; `scripts/heteronyms.test.js` loads its script to test the speak_as column and heteronym warning, `scripts/deckImportReadings.test.js` the reading column). Paste CSV / Google Sheets cells, press Check, then copy the generated SQL into the Supabase SQL editor. It only reads the library (publishable key, read-only look-ups) and never writes; the SQL is safe to run twice (existing textbooks, units, collections, decks and words are reused, nothing is deleted).
- Columns: `school_level, textbook, unit_order, unit, deck, collection, english, japanese, reading, alt_answers, example_en, example_ja, pos, speak_as, source, note` (`english`, `japanese`, `deck` required; a row needs a textbook/unit or a `collection` path like `EIKEN > Grade 3`; `source` / `note` ignored; `speak_as` only fills in words that have none, never overwrites). Errors block the SQL; warnings need a tick first. Heteronyms (same spelling, different pronunciation: read 読む / read 読んだ) without speak_as get a warning; the list lives in `scripts/heteronyms.js` and is copied into the tool (a test checks they match, so change both).
- `pos` (optional): the 12 `words.pos` keys, the app's Japanese labels (名詞 … 表現) or `auxiliary verb`, trimmed and case-insensitive, turned into the keys (`POS_KEYS` / `POS_ALIASES` / `posKey()` in the tool; the keys must match the CHECK in `supabase/polycards-pos.sql`). Anything else = error on that row; the same english + japanese with two different pos values in one file = error (blank on one row is fine). New words are inserted with their pos; an existing word with no pos gets it (`update … where w.pos is null`); an existing word with a DIFFERENT pos keeps it, with a warning showing both. pos only appears in the SQL when the file uses it; if the file uses it and the database has no `words.pos` column, that is an error. Shown in the summary (words with pos), the Decks table (With pos) and the Words table (what happens to each word's pos).
- `reading` (optional, but **every new word should come with one**): the hiragana reading of `japanese` (借りる → かりる, かわいい、きれいな → かわいい、きれいな). Trimmed, spaces collapsed, katakana turned into hiragana (`hiraganaReading()`; ー and ・ kept). Error if it contains kanji, or English letters that are not also in the Japanese meaning (読んだ（readの過去形） → よんだ（readのかこけい） is fine); kana, digits, spaces and punctuation are allowed. Two different readings for the same word in one file = error. A reading that doesn't fit its meaning gets a warning: every run of hiragana in `japanese` must appear in the reading, in the same order (`readingFits()`: 食べる / のむ warns, 読んだ（readの過去形） / よんだ（readのかこけい） doesn't). A blank reading on an all-hiragana meaning (ほほえむ) uses the meaning itself (counted in "words with readings"; a reading typed on another row of the same word wins; not done when the database has no `reading` column). A blank reading on a meaning with kanji or katakana gets a warning (once per word; not when the database already has one). Only ever filled in, never overwritten (`update … where w.reading is null`, run after the word insert, so new words get it too); a different reading already in the database is kept with an info line. Not in the SQL unless the file uses it; an error if the file uses it and the database has no `words.reading` column. The database column is read in its own look-up (like speak_as). Shown in the summary (words with readings) and the check SQL (`with_reading`).
- Example sentences are only filled in where a word has none, unless "Replace existing example sentences" is ticked.
- `alt_answers` (optional): other accepted English answers separated by `;` (or ；), max 80 characters each, no Japanese; merged per word across rows and only ever ADDED to what the word already has (order kept, no repeats, never the main English). ## SRS rules (constants and level logic in `src/lib/srs.js`)
- Levels 0 to 7. Wait before a card is due again, by the level it just reached: `LEVEL_HOURS = [0, 4, 24, 72, 168, 336, 720, 2880]` (new, 4h, 1d, 3d, 1w, 2w, 30d, ~4 months).
- Correct on the first try: level +1. Correct at level 7 = **Mastered** (`MASTERED = 8`, `isMastered()`): never scheduled again, left out of due counts and reviews (`.lt('level', MASTERED)` in `fetchDueRows` / `fetchReviewRows`). A miss at level 7 drops as usual. Mastery is per card (per direction).
- The database works out and saves the level after an answer (`record_answer`), so **`LEVEL_HOURS` and the miss penalty (`levelAfterWrong`) in srs.js must stay in step with `study_level_hours()` and `record_answer` in `supabase/polycards-answers.sql`**. The app still uses `levelAfterCorrect` / `levelUpLabel` for the level-up float. Putting a card back (not an answer) is still written by the app with `restoreUpdate()`: `RESTORED_LEVEL = 1`, due now, `mastered_at` NULL.
- Wrong answers (WaniKani style): the drop is based on how many times the card was missed this session, rounded up in pairs. The 1st and 2nd miss = 1 level down, the 3rd and 4th = 2 levels down, and so on (the first miss already costs a level). From level 5 up the penalty is doubled (1st/2nd miss = 2 levels down). A learned card never drops below level 1; a new card (level 0) stays at 0. The drop is always counted from the level the card had at the start of the session, and the lowered level is saved at each miss.
- A card missed in a session comes back later that session as extra practice. It does not move up again that session.
- Review sessions are capped at the student's 1回の枚数: 10, 20 or 30 (`SESSION_SIZES`, default `DEFAULT_SESSION_SIZE = 20`, chosen in settings, saved on the device).
- These rules are covered by automated tests in `src/lib/srs.test.js` (and drill helpers in `src/lib/drill.test.js`). Run them with `npm test`. If a rule is changed on purpose, update its test in the same change.

## Points and rank
- Each card (one `user_cards` row, so both directions count separately) is worth `CARD_POINTS = [0, 1, 2, 3, 5, 8, 13, 21, 34]` by level (the last entry is Mastered) (in `src/lib/srs.js`, next to `LEVEL_HOURS`). Level 0 cards are worth 0, so adding a deck gives no points until cards are learned.
- Current points = sum over all of the student's `user_cards`. Peak points = highest ever, saved in `user_stats`.
- The player's level is called **Rank** (so it isn't confused with card levels Lv0 to Lv7). The database still calls it `player_level` (`gacha_player_level()` and the `player_level` field of `gacha_status()`); the app treats it as the rank.
- Rank comes from **peak points + spelling bonus points** via `playerRank(peak + bonus)` in `src/lib/points.js` (the only place the formula lives in the app): `floor(sqrt((peak + bonus) / 20)) + 1`, the same as `gacha_player_level()` in the database. The bonus is `user_study_totals.bonus_points` (`fetchBonusPoints()`, own row, `maybeSingle`, 0 if none; loaded with the peak in `loadStats`, and a failed load counts as 0). The saved peak is card points only. Rank 2 at 20 points, Rank 3 at 80, Rank 4 at 180, Rank 10 at 1,620.
- Rank never goes down: removing a deck lowers current points but not the peak.
- Points are recounted each time the dashboard is shown (so after every review), after pending progress saves finish. If the total beats the saved peak, the new peak is upserted to `user_stats`.
- All card levels are read in pages of 1,000 (`fetchAllCardLevels` in `src/lib/api.js`; `fetchDueRows` is paged the same way), so totals are correct beyond Supabase's 1,000-row limit.
- Shown at the top of My Cards by `src/components/PlayerStats.jsx` (avatar, rank labeled ランク and shown as "Rank N", a big gold EXP number = peak + spelling bonus (the same total as the rank and the bar, so it never goes down when cards lose levels; current points are not shown and there is no ベスト line), and a bar showing progress to the next rank, "あと N EXP → Rank N+1"). The avatar box is a button (aria-label ポリアバター図鑑を開く, focus ring from `.avatar-button` in `src/index.css`) that opens the ポリアバター図鑑. The bar uses `pointsForRank()` in `src/lib/points.js`, the reverse of `playerRank()`, and is measured from peak + bonus because the rank comes from them. When the bonus is above 0, a small スペルボーナス N EXP line shows under the EXP number (how much of it came from spelling). Tests: `PlayerStats.test.jsx`. The card count per level is a bar chart in `src/components/LevelChart.jsx` (tests in `LevelChart.test.jsx`): Lv0 to Lv7 plus a 9th Mastered bar in `gold` with a glow (midnight's Lv7 color is also gold), labeled with `StarIcon`. `levelCounts()` returns 9 entries, the last being Mastered.
- Tests: `src/lib/points.test.js` (pure, never touches the database or the test account).

## Handwriting (experimental, branch `handwriting-input`)
Apple Pencil answer mode: students write the English answer one letter per box and a letter model (TensorFlow.js, EMNIST letters a–z, case-insensitive) reads it in the browser. Task spec: `polycards_hw_model/HANDWRITING_TASK.md` (that folder is gitignored; its files were copied into the app). Phase 1 = hidden test page `/hw-test` (approved); Phase 2 = the 手書き answer mode in reviews (built, being tested on the school iPads).

Isolation rules (so it is easy to revert):
- All handwriting code lives in `src/handwriting/`. The only changes outside it: the review screen choosing `<HandwritingInput>` instead of the typing box, the answer-mode setting, and the `/hw-test` hook (`src/main.jsx` checks `isHwTestPath()` and renders `HwTestRoot`; `vercel.json` rewrites `/hw-test` to `index.html`).
- Model files live in `public/models/emnist/` (`model.json` + `group1-shard1of1.bin`; reference data for the self-checks in `test/`).
- **No Supabase or database changes.** A handwriting answer reports its result through the same path typing mode uses (`recordAnswer`).
- `HANDWRITING_ENABLED` in `src/handwriting/config.js` hides the whole feature (and `/hw-test`) when false. `LENIENT_PAIRS`, `MIN_TARGET_PROB`, `LENIENT_GIVES_BONUS`, `STROKE_RATIO` and the handwriting-only colors (paper white, ink black, lenient orange) are there too.
- TensorFlow.js (`@tensorflow/tfjs` 4.x) and the model load **only** through dynamic `import()` (`loadModel()` in `model.js`), so students who don't use handwriting download nothing extra. WebGL backend, `cpu` fallback. The model always runs on a fixed batch of `BATCH_SIZE` (16) images (blank padding, longer answers in chunks of 16) because WebGL recompiles shaders for every new shape (~5 s on an iPad); `warmUp()` runs one blank batch in the background right after loading. Tests: `batch.test.js`.
- Readiness and failures: `modelReady()` (load + warm-up; `isModelReady()` is the synchronous flag) decides when boxes take ink: until then practice boxes and review boxes are dimmed and locked (準備中…, `handwriting.loading` / `practice.loading`), because the warm-up compiles WebGL shaders and can block the page for seconds on a slow iPad. `predictBatch` never runs at the same time as the warm-up. Every read has `RECOGNITION_TIMEOUT_MS` (15 s, `withTimeout()`): a practice box that fails or times out turns neutral with もう一度書いてね (`practice.hint.retry`, ink kept; 3 failures in a row → unavailable); a review read that fails or times out switches to typing as before. A practice box being read shows a small … badge (state `checking`).
- Pen robustness in `LetterBox`: one stroke at a time; a pen always wins (a touch while the pen writes is ignored, a pen drops a touch stroke and takes over); a new pen pointer id ends a stroke whose pen-up was missed; `pointerup` / `pointercancel` are also caught on `window` (a pen-up that misses the canvas would otherwise leave the box waiting forever); the box border has `touch-action: none` too. Finger drawing is still only on `/hw-test` (`allowAnyPointer`).
- Pen debug overlay (`penDebug.js`, tests `penDebug.test.js`): add `?debugpen=1` to the address (kept for the tab in sessionStorage, `?debugpen=0` turns it off). A fixed `pointer-events: none` panel shows the last pen-down (type, position in the box, accepted / rejected and why, how late it was handled; also a pen-down that landed over a box but reached another element), pointercancel count (and whether the page scrolled), lost pointer capture, model status + backend + timings, the last read (ms, result or error) and `navigator.userAgent`. English only (teacher tool); does nothing when off.
- `preprocess.js` (`preprocessLetter`) is the given, tested port of the training preprocessing: use it as is, never replace it with canvas resizing or `ctx.filter`. Boxes are drawn at devicePixelRatio and `getGray()` passes the canvas's real pixel size.
- Files: `config.js`, `model.js`, `preprocess.js`, `answerLayout.js` (`answerSlots`: letters → boxes, spaces → gaps, everything else printed; `printPosition`: printed characters sit by type in a box-high column: apostrophes and quotes at the top (narrow, so "don't" reads as one word), hyphens and dashes in the middle, everything else (. , ... ? ! digits) on the baseline; a run of printed characters is split where the height changes, e.g. "!”"; `boxLayout`: box size, one or two rows), `checkAnswer.js` (`scoreBox` / `scoreWord` / `lenientMessage`: a box is correct when the top letter is the target; lenient (orange + warning naming the letter the model read) when the target still got at least `MIN_TARGET_PROB` (0.25) or the top letter is a `LENIENT_PAIRS` look-alike; otherwise wrong, including an empty box), `selfCheck.js`, `LetterBox.jsx` (one canvas; only `pointerType === "pen"` draws unless `allowAnyPointer`. ## How to work with me
- Make small, focused changes. Before large refactors (like reorganizing folders or moving logic between many files), propose a plan and wait for approval.
- After a change, run `npm test`, `npm run lint` and `npm run build`, then summarize in a few plain sentences what changed and how I can test it.
- If you are not certain a step or command is correct, say so instead of guessing.
- Work on a branch, not on `main`. Suggest a git commit message after each working change.
- Never push to `main` (or merge into it) unless I say so, because that deploys to students. Don't push other branches unless I ask.
