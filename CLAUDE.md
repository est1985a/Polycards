# Polycards

A vocabulary spaced-repetition (SRS) web app for Japanese junior high and high school students learning English. Think WaniKani or Anki, built for my classes at Ryukoku Junior/Senior High School. I'm an English teacher, not a professional developer, so explain changes in plain language.

## Stack
- React + Vite. Code layout:
  - `src/App.jsx`: shared state (session, screen, My Cards data) and which screen to show
  - `src/components/`: one file per screen part (`StudySession`, `MyCardsTab`, `MasteredList`, `StarIcon`, `CardSetsTab`, `CardSetsHub`, `NavRow`, `LevelSwitch`, `LoginScreen`, `Header`, `LogoMark`, `Tabs`, `Stamp`, `PlayerStats`, `LevelChart`, `ReviewPlanSheet`, `Avatar`, `AvatarPicture`, `FlipCard`, `WordInfo`, `WordList`, `Highlighted`, `AddDeckButton`, `GachaScreen`, `GachaReveal`, `GachaCollection`, `GachaMachine`, `GachaIcons`, `ToggleSwitch`, `SettingsScreen`, `StatsScreen`, `ThemePreview`, `ThemeUnlockSheet`, `SpeakerButton`)
  - `src/lib/srs.js`: SRS rules, plus `srsAnswer()` (what one review answer sends and shows) `newSessionId()` and `saveErrorReporter()`; `src/lib/spelling.js`: typing-mode spelling check (a copy of `spelling_check()` in the SQL), the other-meaning retry rule and the typing-mode setting (pure functions); `src/lib/points.js`: points and rank (pure functions); `src/lib/drill.js`: building/shuffling card piles; `src/lib/dictionary.js`: builds the dictionary link for a word; `src/lib/library.js`: shapes the Card Sets library and its back-button rules (pure functions); `src/lib/schedule.js`: next-review wording and the review plan, in Japan time (pure functions); `src/lib/sheet.js`: when a pop-up closes; `src/lib/gacha.js`: rarity labels/colors, ticket progress, collection grouping, and `singleFlight()` for the pull button (pure functions); `src/lib/settings.js`: settings saved on the device (session size, reduce motion, auto-play, slow speech, theme cache, seen themes; try/catch); `src/lib/speech.js`: pronunciation with the browser's speech (`speechText()`, `speechAvailable()`, `speakWord()`, `stopSpeaking()`); `src/lib/themeUnlocks.js`: which themes are unlocked / new at a rank (pure functions); `src/lib/studyStats.js`: streaks and the month calendar / chart for the stats page (pure functions); `src/lib/screens.js`: settings / stats stacking for 戻る (pure functions); `src/lib/undo.js`: the session snapshot for undoing the last まだ / わかった (pure functions); `src/lib/api.js`: every Supabase query (and `recordAnswer`, the only way review answers are saved); `src/lib/supabaseClient.js`: creates the Supabase client
  - `src/handwriting/`: the experimental Apple Pencil handwriting mode, kept separate (see Handwriting below)
  - `src/i18n/`: all student-facing text: `ja.js`, `en.js` (same keys) and `index.js` (`t()`, `tx()`, `getLang()`, `setLang()`); see Languages below
  - `src/styles/theme.js`: shared colors (as CSS variables), fonts, and button styles
  - `src/themes.js`: color themes (values for each color role) and `applyTheme()`
- Supabase: PostgreSQL, Auth, Row Level Security
- Sign-in: Google OAuth, open to any Google account. Signing in is required; the old "Skip login (Test App)" bypass has been removed. Email/password is enabled in Supabase but has no sign-in screen in the app.
- Deployed on Vercel at https://polycards-eight.vercel.app. Vercel redeploys automatically on every push to `main`, so a push to `main` goes live. For now the live site is for teacher testing only; students don't have access yet.

## Database (Supabase)
Library tables (read-only for everyone, I add content myself in the Supabase SQL editor):
- `textbooks` (id, name, school_level: `JHS` | `HS` | `Other`)
- `units` (id, textbook_id, name, unit_order)
- `decks` (id, unit_id, name)
- `words` (id uuid, english, japanese, example_en, example_ja, alt_answers): one shared word list; a word can appear in several decks. `example_en` / `example_ja` are optional example sentences (some words don't have them yet). `alt_answers text[] not null default '{}'` = other English answers also accepted in typing / handwriting (see Alternate answers below; added by `supabase/polycards-alt-answers.sql`). Recorded audio (`supabase/polycards-word-audio.sql`, which must be run before deploying app code that selects `audio_path`): `speak_as` (record this text instead of the English, e.g. 'How old are you?'), `audio_path` (file in the `word-audio` bucket), `audio_text` (exact text recorded), `audio_voice` (voice used); the last three are written only by `npm run audio`
- `deck_words` (deck_id, word_id, position): which words are in which deck
- `collections` (id, name, parent_id, sort_order): the Tests & Themes tree, up to 4 levels deep (top level = `parent_id` null). `collection_decks` (collection_id, deck_id) links decks to collections; those decks have `unit_id` null. First real one: 小学校の英語 (40 decks, "1 あいさつ" … "40 疑問詞", imported with the Deck Import Tool SQL).
- Word ids are **uuids, not numbers**: `words.id` and every `word_id` (`deck_words`, `user_cards`, `counted_cards`, `answer_log`, and `record_answer`'s `p_word_id`). `supabase/polycards-fix-word-id.sql` (2026-10-16) changed `counted_cards.word_id`, `answer_log.word_id` and `record_answer` from bigint to uuid (that bug made every review save fail with 保存できませんでした and stopped the gacha review counter); `polycards-gacha.sql` and `polycards-answers.sql` are updated to match.
- `cards` is the OLD per-deck word table. It still exists but must not be used.

Per-student tables (RLS: each user can only touch their own rows; `user_id` defaults to `auth.uid()`):
- `user_decks` (user_id, deck_id, added_at): decks added to My Cards
- `user_cards` (user_id, word_id, direction, level, next_review_at, mastered_at, updated_at): progress per word AND direction, primary key (user_id, word_id, direction). Level 8 = Mastered: `next_review_at` is NULL and `mastered_at` is when it was mastered (NULL for every other level). CHECK constraint `user_cards_level_range` allows level 0 to 8. Progress belongs to the word, not the deck, so a shared word has one level across all of a student's decks.
- `user_stats` (user_id primary key default `auth.uid()`, peak_points, updated_at): highest points the student has ever had. RLS own row only; the trigger `user_stats_keep_peak` keeps `peak_points` at the highest value ever saved.

Gacha tables (created by `supabase/polycards-gacha.sql`; students may only SELECT, and only some of them):
- `avatars` (id, slug, name_ja, name_en, rarity: `normal` | `rare` | `super_rare` | `secret`, series, image_url (NULL = placeholder picture), is_starter, active, sort_order): no direct access for students, so Secret names stay hidden.
- `user_avatars` (user_id, avatar_id, obtained_at): who owns which avatar.
- `user_gacha` (user_id, reviews_counted, tickets_spent, pulls_since_secret, equipped_avatar_id, theme): one row per student.
- `counted_cards` (user_id, word_id, direction, last_counted_at): which cards were counted as a review (functions only).
- `theme_unlocks` (theme_key, unlock_level): `unlock_level` is the rank needed.
- Reviews are counted by the trigger `user_cards_count_review` on `user_cards` (a due card whose schedule changes = one review; the same card at most once per 3 hours). Tickets: 1 after the first review, +1 per 100 reviews (review tickets capped at 1 per day, `supabase/polycards-ticket-daily-cap.sql`), +1 every 10th rank, minus tickets used. Settings live in `gacha_setting()`.

Gacha functions. **The app only calls these RPCs (`supabase.rpc`, in `src/lib/api.js`); it never reads or writes the gacha tables directly and never counts reviews or tickets itself.** One exception: `theme_unlocks` is read directly (`fetchThemeUnlocks`, once after sign-in), because the unlock ranks are needed for the theme picker.
- `gacha_status()` → `{ tickets, reviews_counted, reviews_to_next_ticket, reviews_per_ticket, next_ticket_tomorrow (true = today's review ticket is already earned), remaining, owned, total, odds: { normal, rare, super_rare, secret } (percent, live: from the rarities the student still lacks), player_level (= the rank), equipped_avatar: { id, slug, name_ja, name_en, rarity, image_url }, theme }` (`fetchGachaStatus`)
- `gacha_pull()` → `{ avatar: { id, slug, name_ja, name_en, rarity, series, image_url }, tickets_left }`; always an avatar the student doesn't have; locks the student's row so two taps can't spend one ticket twice (`pullGacha`)
- `gacha_collection()` → rows `{ id, slug, rarity, series, sort_order, owned, obtained_at, equipped, name_ja, name_en, image_url }`; unowned rows have no slug/name, unowned Secrets also no picture (`fetchGachaCollection`)
- `gacha_equip_avatar(p_avatar_id)` (`equipAvatar`), `gacha_set_theme(p_theme)` (`setGachaTheme`, used by the theme picker and the unlock pop-up)
- Error codes → messages (`gachaErrorMessage()`): `no_tickets` ガチャ券がありません, `collection_complete` 全部そろいました！新しいアバターをお楽しみに, `not_owned` このアバターはまだ持っていません, `theme_locked` このテーマはまだ使えません, `not_signed_in` ログインしてください.

Answer log and study stats (created by `supabase/polycards-answers.sql`, run after the gacha SQL; students may only SELECT their own rows, only `record_answer()` writes them):
- `answer_log` (id, user_id, session_id, word_id, direction, result: `got_it` | `not_yet` | `dont_know`, is_repeat, typed, typed_answer, spelling: `exact` | `close` | `wrong`, level_before, level_after, bonus_points, answered_at): one row per answer in a review.
- `user_study_daily` (user_id, day (Japan date), reviews, got_it, not_yet, dont_know, repeats, typed, spelled_correctly, bonus_points): totals per student per day. `reviews` = first answers only; repeats are counted separately.
- `user_study_totals` (user_id, same counters, updated_at): all-time totals. `bonus_points` (spelling bonus) now counts toward rank: `gacha_player_level()` = `floor(sqrt((peak + bonus) / 20)) + 1`.
- Settings in `study_setting()` (spelling bonus, answer_log cleanup, which is built but OFF). Spelling check functions (`spelling_normalize`, `spelling_distance`, `spelling_check`) are used by typing mode; **`src/lib/spelling.js` must give the same results as them** (the app's copy only shows ✓ / おしい instantly; the database decides the bonus).

`record_answer(p_word_id uuid, p_direction text, p_result text, p_session_id uuid, p_typed text default null)` → `{ result, is_repeat, level_before, level_after, mastered, spelling, bonus_points, bonus_total }`. It works out the new level itself (same rules as `src/lib/srs.js`), saves the `user_cards` row, logs the answer and adds to the daily/total stats; the gacha review counter trigger still runs. `p_result`: `got_it` (わかった), `not_yet` (まだ), `dont_know` (わからない, not used yet). An answer is a repeat when the same card was already answered with the same session id; a repeat わかった is logged but changes no level. Errors: `not_signed_in`, `bad_answer`, `card_not_found`, `not_due` (a first answer on a card that isn't due).
- **Review answers are saved only through `record_answer`**: `recordAnswer(card, result, sessionId)` in `src/lib/api.js`. The app never writes `user_cards` levels after an answer. Answers are sent one at a time, in the order they were given (a queue: each waits for the previous one; a failed one doesn't block the next), and each is tracked in `pendingSaves` so `waitForPendingSaves()` still holds points/tickets until saves finish. Errors: `not_due` → only `console.warn`; `card_not_found` → このカードは見つかりませんでした; `not_signed_in` → ログインしてください; anything else → 保存できませんでした (`answerErrorMessage()`). Every failure is logged with `console.error`, but the pop-up shows at most once per review session (`saveErrorReporter()` in srs.js, one per `StudySession`).
- `StudySession` makes one session id per review (`newSessionId()` in srs.js: `crypto.randomUUID()`, with a hand-built UUID v4 fallback for older browsers / plain-http addresses) and calls `recordAnswer` for every SRS answer (わかった → `got_it`, まだ → `not_yet`), including わかった on a card missed earlier. The Card Sets drill writes nothing.
- **Undo (元に戻す) for the last まだ / わかった** (SRS review and the Card Sets drill, including the まだ / わかった choice after a close or wrong typing / handwriting answer): the answer is not sent at once but **held** (`holdAnswer` / `flushHeldAnswer` / `dropHeldAnswer` in `api.js`, one at most). It is sent (through `recordAnswer`, so in order and in `pendingSaves`) when the next answer is given, when `StudySession` closes (a `useLayoutEffect` cleanup, which runs before App's effects wait for pending saves and recount points / tickets), on `pagehide` / `visibilitychange` to hidden (the chip disappears), and before sign out (`handleLogout` flushes and waits before `signOut`). A correct spelling (typing or handwriting) and わからない are not undoable: they send the held answer first, then themselves at once. Undo drops the held answer and puts back the session from just before it (`takeSnapshot` / `restoreState` in `src/lib/undo.js`: pile incl. removing the re-inserted まだ card, miss counts, cleared count, drill counts, typed / typedResult / retryUsed), with the card on top already flipped (new turn key) and any Lv / Mastered / +1 スペル float cleared. One step only. A handwriting read that finishes after an undo is ignored (turn check); an undone handwriting card shows its colored boxes and 読み取り line but not the pencil strokes.
  - The chip (`PreviousCardChip` in `StudySession.jsx`): 前のカード, the card's front word, ✓ わかった (`accentText`) or まだ (`danger`) (the existing button text), and 元に戻す (44 px, `review.undoAria`). Beside the card only when there is room: centered in the space between the screen edge and the card (`width: calc(50vw - 50%)`), vertically centered on the card, max 150 px, contents centered in one column, a fixed 96 px button (same in ja / en, still 44 px tall); the word is cut to 3 lines with … (line clamp, `overflow-wrap: anywhere`). That needs `useSideChip()` / `SIDE_CHIP_QUERY` (1150 px) in `useWide.js`, App passes `sideChip`. Otherwise a row above the question line (word cut to 1 line); after the first answer that row keeps its 44 px height for the rest of the session, so the card doesn't jump. Also on the 全部クリアしました！ panel. No animation. Tests: `src/lib/undo.test.js`, `api.test.js` (held answer), `StudySession.test.jsx` (chip), `useWide.test.js`.
- Tests: `src/lib/api.test.js` (arguments, order, errors, no `user_cards` write), `StudySession.test.jsx` (`srsAnswer`, `newSessionId`, `saveErrorReporter`, `PreviousCardChip`).

`other_meaning_check(p_word_id uuid, p_typed text)` → boolean (from `supabase/polycards-other-meaning.sql`): true when what was typed is exactly another library word that shares a Japanese meaning with this card (e.g. "from" on the から card that wants "since"). Saves nothing. Called only by `checkOtherMeaning(wordId, typed)` in `src/lib/api.js`, which never throws: an error → `console.warn` and false.

Shared-word rules:
- Adding a deck creates `user_cards` rows for each of its words in both directions and skips words the student already has, so existing progress is kept.
- Removing a deck deletes progress only for words that are not in any of the student's other added decks.
- Per-deck due counts count a shared word under every added deck that contains it, so per-deck numbers can add up to more than the "Due now" total.

Rules:
- Never change the schema or RLS yourself. Write the SQL in a separate block and I will run it in the Supabase SQL editor.
- Never commit secrets. The anon key is public by design, but a service-role key must never appear in the repo. The recording script's keys (`GOOGLE_TTS_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_URL`) live only in `.env.audio` (repo root, in `.gitignore`; Vite never loads it); nothing in `src/` may read it.
- **After adding new words (or editing an English word or its `speak_as`) via SQL, run `npm run audio` (on the Mac or the Windows PC) to record them.** Until then those words use the built-in voice.
- Supabase returns at most 1,000 rows per query; keep that in mind for large lists.

## App structure
- Two dashboard tabs: **My Cards** (decks the student added, due counts, SRS review) and **Card Sets** (global library).
- Card Sets navigation (no router, same `useState` pattern as `view`): hub (`CardSetsHub.jsx`: two big cards, Textbooks in `accent` and Tests & Themes in `gold`, with low-poly decorations) → textbooks (a segmented switch 中学 · JHS | 高校 · HS, plus Other only when such textbooks exist, shows one level at a time, by name; `LevelSwitch.jsx`) → units (by `unit_order`) → decks (by name, with word count) → word list. Tests & Themes → top-level collections (`NavRow`s by sort_order then name, pill = decks inside, sub-collections included, each deck once) → a collection (its sub-collections first, then its decks by sort_order then name numeric-aware, with word count and the 追加済み badge) → as deep as the tree goes → the same word list / drill / Add to My Cards as textbook decks (`startDeck`). 準備中 — Coming soon shows only when there are no collections at all. The tree comes from `fetchCollections()` in api.js (two queries, `collections` and `collection_decks ( decks ( …, deck_words ( count ) ) )`, both through `fetchAllPages`), shaped by `shapeCollections()` in `library.js` (`findCollection()`, `collectionParentPath()`: back goes to the parent collection, or to Tests & Themes from the top). It loads with the library (`collectionsData` in App, null until loaded = 読み込み中; a failed load only `console.error`s and counts as no collections); a collection that no longer exists falls back to Tests & Themes. The current screen is `cardSetsPath` in App.jsx (`{ screen: 'hub' | 'tests' | 'collection' | 'textbooks' | 'units' | 'decks', textbookId, unitId, collectionId, level }`), kept in App so coming back from a word list or drill returns to the same deck list. Each list screen has a ← back button that goes up one level (`parentPath()`); tapping the Card Sets tab while on it returns to the hub; a textbook/unit that no longer exists falls back to the hub (`resolvePath()`). The chosen level is kept on every screen (back returns to the same level) and saved in localStorage key `polycards.cardSetsLevel` (`loadSchoolLevel`/`saveSchoolLevel`, wrapped in try/catch; JHS if nothing is saved). The phone's own Back gesture does not step through these screens. List rows are `NavRow.jsx` (same look as the マイデッキ rows; optional `badge` before the pill). On the deck list, decks already in My Cards show a ✓ 追加済み pill (`accent` fill, inline SVG check), using `myDeckIds` that App already loads (`isDeckAdded()` in `library.js`, no extra query); it appears right after Add to My Cards because `addDeck` reloads `myDeckIds`. The library is one query (`fetchLibrary`), and `deck_words ( count )` returns each deck's word count without loading the words; `shapeLibrary()` turns it into `wordCount`. Tests: `src/lib/library.test.js`, `CardSetsTab.test.jsx`.
- Card Sets: opening a deck first shows a word list (`WordList.jsx`, view `wordList` in App.jsx): every word in deck order with its example sentence (word highlighted in gold by `Highlighted.jsx`), a 日本語をかくす switch (sticky at the top with a `bg` background while the list scrolls) that covers each Japanese word with a タップで表示 block (a 44 px button the same size as the word, so rows don't jump; tap to show that word and its example translation, tap again to hide; the example translation is blurred while hidden). Reveals are a Set of word ids in `WordList` (`toggleId()` in `library.js`), cleared when the switch changes and reset when the deck is left (App gives `WordList` `key={activeSet.id}`). There is also a fixed ドリルを始める (Start drill) button at the bottom. No extra query: it uses the cards `startDeck` already built. The button runs the older "try it" drill (a card is cleared after `CLEAR_TARGET = 2` correct answers, set in `src/lib/drill.js`; wrong answers re-insert the card). Students can add the deck to My Cards from the list or the drill (`AddDeckButton.jsx`). SRS review in My Cards has no word list. Tests: `WordList.test.jsx`.
- The app always opens on the My Cards tab (`activeTab` starts as `myCards`; nothing about the tab is saved). Card Sets starts at its hub; only the school level is remembered.
- My Cards: real SRS review. The 2-correct drill does NOT apply here. Decks can also be removed from My Cards.
- Typing mode (答え方 タイピング, SRS review only, Japanese → English cards only; en2jp cards and the Card Sets drill are unchanged):
  - Answer-mode switch on My Cards right under the level chart (`AnswerModeSwitch` in `MyCardsTab.jsx`, segmented like `LevelSwitch`): 答え方（日本語 → English） with なし / タイピング / 手書き and a note for the chosen one (タイピング: 英語をタイプして答えます。正しいスペルで +1 pt). 手書き is hidden when `HANDWRITING_ENABLED` is false. Off by default; saved on the device in localStorage `polycards.answerMode` = `off` | `typing` | `handwriting` (`loadAnswerMode` / `saveAnswerMode` in `spelling.js`, try/catch; the old `polycards.typingMode` = "1" loads as typing; a saved 手書き loads as typing when handwriting is switched off). Held in App (`answerMode`) and passed to `StudySession` (`answerMode` prop).
  - `TypingArea` in `StudySession.jsx` replaces 答えを見る: a text box (`autoComplete="off" autoCorrect="off" autoCapitalize="none" spellCheck={false} lang="en"`, focused when the card appears), 答える (Enter also works; disabled while empty; an Enter that only confirms Japanese-keyboard input is ignored) and わからない.
  - Result from `checkSpelling(typed, card.en)`: **exact** → card flips, ✓ 正解！ (`accentText`), "+1 スペル" float (gold, top-left of the card, class `spell-bonus-float`, only fades with reduce motion; not shown on a card missed earlier this session), the usual Lv / Mastered float, `record_answer` sent at once as `got_it` with the typed text, then 次へ. **close** → card flips, おしい！ (gold), あなたの答え / 正しい答え, then the normal まだ / わかった; the choice is sent with the typed text (held, so it can be undone; see Undo above). **wrong** → the same without おしい！. **わからない** → `dont_know` sent at once (no typed text), counts as a miss (card comes back), card flips, then 次へ.
  - Alternate answers (`words.alt_answers`, SQL `supabase/polycards-alt-answers.sql`, run after `polycards-answers.sql`, `polycards-fix-word-id.sql` and `polycards-other-meaning.sql`; it must be run before deploying app code that selects `alt_answers`): a typed answer is checked against the main english AND every alternate, with exactly the same clean-up and close rules (`spellingAnswers()` / `checkSpelling(typed, english, alts)` in `spelling.js` = `spelling_answers()` / the 3-argument `spelling_check()` in SQL; the 2-argument `spelling_check` still exists and means no alternates). An exact alternate is the normal exact flow (`got_it`, +1 スペル, Lv float, bonus from `record_answer`); the student's answer is shown before the tick in a lighter weight, same color, `lang="en"` (huge ✓ 正解！; typed text trimmed, or the accepted alternate in handwriting; `alternateAnswer` prop of `TypingArea`), plus a small `gold` line under ✓ 正解！: 教科書の答え: <main english> (`review.textbookAnswer`, `textbookAnswer` prop of `TypingArea`, shown when `isAlternateAnswer()`). Close to an alternate = おしい, with 正しい答え still the main english. An exact alternate never gets the other-meaning retry; `other_meaning_check` also returns false for the card's own alternates and counts other words' alternates as their spellings. Cards carry `altAnswers` (`wordFields()` in drill.js, `[]` if none); `fetchDeckWords` / `fetchReviewRows` load `alt_answers`. To add one: `update public.words set alt_answers = '{cute}' where english = 'pretty' and japanese = 'かわいい、きれい';`
  - Other meaning, one retry: when `checkSpelling` says **wrong** (never for exact / close), and this showing of the card hasn't had its retry yet (`needsOtherMeaningCheck()` in `spelling.js`), the app first calls `checkOtherMeaning(card.wordId, typed)`; meanwhile 答える shows 確認中… and is disabled (わからない and typing in the box too). True → no flip, nothing saved, no miss counted: the box is cleared and keeps focus (答える doesn't take focus on tap, so the keyboard stays open), and a calm `gold` line (`role="status"`) under the box says それも正しい意味ですが、この単語ではありません。もう一度！. The next answer is still the first saved answer, so a correct spelling earns the bonus; a second wrong answer is just wrong. False or a failed call → the normal wrong flow (only `console.warn`, never a pop-up). State `checking` / `retryUsed` in `StudySession`, reset in `finishAnswer()`, so a card that comes back later gets a fresh retry; a check that answers after the card has moved on is ignored.
  - 次へ gets focus so Enter works, but ignores held-down keys and any Enter in the first 300 ms (`ignoreNextKey()`, `NEXT_KEY_GUARD_MS`), so the Enter that answered can't skip the result.
  - Keyboard (landscape iPad): while typing, `FlipCard` is `compact` (150 px / 180 px wide, front not tappable, back drawn only after it flips), and when `visualViewport` resizes (keyboard opens) the page scrolls so the question line is at the top, keeping the word, box and buttons above the keyboard. Not yet checked on a real iPad.
  - If the database's `spelling` differs from the app's, only `console.warn`. `srsAnswer(level, result, wrongsSoFar, spelling)` takes `'got_it' | 'not_yet' | 'dont_know'` and returns `spellingBonus`; `recordAnswer(card, result, sessionId, typed)` adds `p_typed` only when there is typed text.
  - Tests: `src/lib/spelling.test.js` (all clean-up / exact / close / wrong cases, alternates, `needsOtherMeaningCheck`), `StudySession.test.jsx` (`TypingArea` incl. 確認中… and the retry note, `srsAnswer`), `MyCardsTab.test.jsx`, `FlipCard.test.jsx`, `api.test.js` (incl. `checkOtherMeaning` arguments and error fallback). The tests can't tap buttons, so "no save on a retry" rests on `handleTypedAnswer` returning before `send()`.
- Level-up float (SRS review only, not the drill), drawn in `StudySession.jsx`: a clean correct answer shows a small "Lv N!" (Chakra Petch 15 px, `accentText`, class `level-up-tick`) that rises 14 px from just above the level chip in the card's top-right corner (`right: 22`, lined up with `LevelChip` in `FlipCard.jsx`) and fades over 0.8 s (keyframes `polycards-level-tick`). ## SRS rules (constants and level logic in `src/lib/srs.js`)
- Levels 0 to 7. Wait before a card is due again, by the level it just reached: `LEVEL_HOURS = [0, 4, 24, 72, 168, 336, 720, 2880]` (new, 4h, 1d, 3d, 1w, 2w, 30d, ~4 months).
- Correct on the first try: level +1. Correct at level 7 = **Mastered** (`MASTERED = 8`, `isMastered()`): never scheduled again, left out of due counts and reviews (`.lt('level', MASTERED)` in `fetchDueRows` / `fetchReviewRows`). A miss at level 7 drops as usual. Mastery is per card (per direction).
- The database works out and saves the level after an answer (`record_answer`), so **`LEVEL_HOURS` and the miss penalty (`levelAfterWrong`) in srs.js must stay in step with `study_level_hours()` and `record_answer` in `supabase/polycards-answers.sql`**. The app still uses `levelAfterCorrect` / `levelUpLabel` for the level-up float. Putting a card back (not an answer) is still written by the app with `restoreUpdate()`: `RESTORED_LEVEL = 1`, due now, `mastered_at` NULL.
- Wrong answers (WaniKani style): the drop is based on how many times the card was missed this session, rounded up in pairs. The 1st and 2nd miss = 1 level down, the 3rd and 4th = 2 levels down, and so on (the first miss already costs a level). From level 5 up the penalty is doubled (1st/2nd miss = 2 levels down). A learned card never drops below level 1; a new card (level 0) stays at 0. The drop is always counted from the level the card had at the start of the session, and the lowered level is saved at each miss.
- A card missed in a session comes back later that session as extra practice. It does not move up again that session.
- Review sessions are capped at the student's 1回の枚数: 10, 20 or 30 (`SESSION_SIZES`, default `DEFAULT_SESSION_SIZE = 20`, chosen in settings, saved on the device).
- These rules are covered by automated tests in `src/lib/srs.test.js` (and drill helpers in `src/lib/drill.test.js`). Run them with `npm test`. If a rule is changed on purpose, update its test in the same change.

## Points and rank
- Each card (one `user_cards` row, so both directions count separately) is worth `CARD_POINTS = [0, 1, 2, 3, 5, 8, 13, 21, 34]` by level (the last entry is Mastered) (in `src/lib/srs.js`, next to `LEVEL_HOURS`). Level 0 cards are worth 0, so adding a deck gives no points until cards are learned.
- Current points = sum over all of the student's `user_cards`. Peak points = highest ever, saved in `user_stats`.
- The player's level is called **Rank** (so it isn't confused with card levels Lv0 to Lv7). The database still calls it `player_level` (`gacha_player_level()` and the `player_level` field of `gacha_status()`); the app treats it as the rank.
- Rank comes from **peak points + spelling bonus points** via `playerRank(peak + bonus)` in `src/lib/points.js` (the only place the formula lives in the app): `floor(sqrt((peak + bonus) / 20)) + 1`, the same as `gacha_player_level()` in the database. The bonus is `user_study_totals.bonus_points` (`fetchBonusPoints()`, own row, `maybeSingle`, 0 if none; loaded with the peak in `loadStats`, and a failed load counts as 0). The saved peak is card points only. Rank 2 at 20 points, Rank 3 at 80, Rank 4 at 180, Rank 10 at 1,620.
- Rank never goes down: removing a deck lowers current points but not the peak.
- Points are recounted each time the dashboard is shown (so after every review), after pending progress saves finish. If the total beats the saved peak, the new peak is upserted to `user_stats`.
- All card levels are read in pages of 1,000 (`fetchAllCardLevels` in `src/lib/api.js`; `fetchDueRows` is paged the same way), so totals are correct beyond Supabase's 1,000-row limit.
- Shown at the top of My Cards by `src/components/PlayerStats.jsx` (avatar, rank labeled ランク and shown as "Rank N", current and peak points (the ベスト line shows only when the peak is higher than the current points), and a bar showing progress to the next rank, "あと N pt → Rank N+1"). The avatar box is a button (aria-label アバター図鑑を開く, focus ring from `.avatar-button` in `src/index.css`) that opens the アバター図鑑. The bar uses `pointsForRank()` in `src/lib/points.js`, the reverse of `playerRank()`, and is measured from peak + bonus because the rank comes from them. When the bonus is above 0, a small スペルボーナス N pt line shows under ベスト. Tests: `PlayerStats.test.jsx`. The card count per level is a bar chart in `src/components/LevelChart.jsx` (tests in `LevelChart.test.jsx`): Lv0 to Lv7 plus a 9th Mastered bar in `gold` with a glow (midnight's Lv7 color is also gold), labeled with `StarIcon`. `levelCounts()` returns 9 entries, the last being Mastered.
- Tests: `src/lib/points.test.js` (pure, never touches the database or the test account).

When text should look like the accent (the rank "Rank 3"), use `accentText`: the same color as `accent` in midnight and pizza, a darker coral in lagoon so it passes contrast. Points and other big numbers use `gold`, headings and links use `text`/`muted`, "Still learning" uses `btnDanger`.
- `src/themes.test.js` checks that every theme has every role and that text passes WCAG 4.5:1 contrast. A new theme must pass it.
- Trying a theme: only under `npm run dev`, add `?theme=galaxy` (any theme key) to the URL; while it is there the saved theme is not applied. Ignored on the live site (`devThemeOverride()` in settings.js).
- Fonts (Google Fonts, loaded in `index.html`): Chakra Petch for headings and numbers (`fontDisplay`), Zen Maru Gothic for body and Japanese (`fontBody`).

## Languages (Japanese / English)
- **All student-facing text goes in `src/i18n/ja.js` AND `src/i18n/en.js`, with the same keys.** Menus, buttons, messages, aria-labels and alerts all count. Never write student-facing text directly in a component or `lib/` file; add a key to both files and use `t()` / `tx()`.
- **The guard test enforces it:** `src/i18n/guard.test.js` fails on any Japanese character in a code line (comments don't count) in `src/components/`, `src/lib/`, `src/content/`, `src/handwriting/` and `App.jsx`. Allowed: `LoginScreen.jsx`, `src/lib/login.js`, `src/i18n/`, `HwTestPage.jsx`, `HwTestRoot.jsx`, `selfCheck.js`, test files, the Japanese punctuation in `spelling.js`'s `.replace(` rules, and the ThemePreview sample word よく知られた. `src/i18n/dictionaries.test.js` checks that both files have the same keys and that English uses no placeholder the Japanese entry lacks (it may use fewer, e.g. no `{nameJa}`).
- `t(key, vars)` fills placeholders like `{n}`; `tx(key, vars)` is for a placeholder that is a styled React element. A function entry is called with the vars first and returns text that still contains `{n}`, which is then filled in. A key missing in `en.js` falls back to `ja.js` (with a warning in development). `""` means "show nothing here" (the Japanese line of the answer buttons, `cardSets.titleJa`), so code must skip empty text.
- **Plurals in `en.js` are functions** (`plural("{n} word", "{n} words")`). **Every `tx()` call that shows a number also passes the plain number as `count`**, because the function can't read a number inside a styled element: `tx("cardSets.wordCount", { n: <span>…</span>, count: deck.wordCount })`. `time.monthDay` gets `month` as 1–12.
- The language is a device setting (`loadLang` / `saveLang` / `applyLang` in `src/lib/settings.js`), applied in `main.jsx` before the first render, held in App (`lang`) and switched with no reload (App's state change re-renders everything; all text is looked up at render time, so never cache translated text in module-level constants). `<html lang>` follows it while signed in.
- **The login screen stays Japanese** whatever the setting (`<html lang="ja">` while signed out).
- English mode shows avatar names in English only (the gacha reveal hides `name_ja`); review-plan hours (18:00) are the same in both languages.
- English text is simple English for JHS students (American spelling). **Andre chooses the English wording; Claude Code doesn't invent student-facing text.** For a new feature, add the Japanese key and ask for the English, or propose wording clearly marked as a draft.
- Tests: `src/i18n/index.test.jsx` (`t()` / `tx()`, fallback, plurals), `dictionaries.test.js`, `english.test.jsx` (key screens in English and back), `guard.test.js`, `src/lib/settings.test.js` (`polycards.lang`).

## Handwriting (experimental, branch `handwriting-input`)
Apple Pencil answer mode: students write the English answer one letter per box and a letter model (TensorFlow.js, EMNIST letters a–z, case-insensitive) reads it in the browser. Task spec: `polycards_hw_model/HANDWRITING_TASK.md` (that folder is gitignored; its files were copied into the app). Phase 1 = hidden test page `/hw-test` (approved); Phase 2 = the 手書き answer mode in reviews (built, being tested on the school iPads).

Isolation rules (so it is easy to revert):
- All handwriting code lives in `src/handwriting/`. The only changes outside it: the review screen choosing `<HandwritingInput>` instead of the typing box, the answer-mode setting, and the `/hw-test` hook (`src/main.jsx` checks `isHwTestPath()` and renders `HwTestRoot`; `vercel.json` rewrites `/hw-test` to `index.html`).
- Model files live in `public/models/emnist/` (`model.json` + `group1-shard1of1.bin`; reference data for the self-checks in `test/`).
- **No Supabase or database changes.** A handwriting answer reports its result through the same path typing mode uses (`recordAnswer`).
- `HANDWRITING_ENABLED` in `src/handwriting/config.js` hides the whole feature (and `/hw-test`) when false. `LENIENT_PAIRS`, `MIN_TARGET_PROB`, `LENIENT_GIVES_BONUS`, `STROKE_RATIO` and the handwriting-only colors (paper white, ink black, lenient orange) are there too.
- TensorFlow.js (`@tensorflow/tfjs` 4.x) and the model load **only** through dynamic `import()` (`loadModel()` in `model.js`), so students who don't use handwriting download nothing extra. WebGL backend, `cpu` fallback. The model always runs on a fixed batch of `BATCH_SIZE` (16) images (blank padding, longer answers in chunks of 16) because WebGL recompiles shaders for every new shape (~5 s on an iPad); `warmUp()` runs one blank batch in the background right after loading. Tests: `batch.test.js`.
- `preprocess.js` (`preprocessLetter`) is the given, tested port of the training preprocessing: use it as is, never replace it with canvas resizing or `ctx.filter`. Boxes are drawn at devicePixelRatio and `getGray()` passes the canvas's real pixel size.
- Files: `config.js`, `model.js`, `preprocess.js`, `answerLayout.js` (`answerSlots`: letters → boxes, spaces → gaps, everything else printed; `printPosition`: printed characters sit by type in a box-high column: apostrophes and quotes at the top (narrow, so "don't" reads as one word), hyphens and dashes in the middle, everything else (. , ... ? ! digits) on the baseline; a run of printed characters is split where the height changes, e.g. "!”"; `boxLayout`: box size, one or two rows), `checkAnswer.js` (`scoreBox` / `scoreWord` / `lenientMessage`: a box is correct when the top letter is the target; lenient (orange + warning naming the letter the model read) when the target still got at least `MIN_TARGET_PROB` (0.25) or the top letter is a `LENIENT_PAIRS` look-alike; otherwise wrong, including an empty box), `selfCheck.js`, `LetterBox.jsx` (one canvas; only `pointerType === "pen"` draws unless `allowAnyPointer`. Pointer and touch listeners are attached with `addEventListener(..., { passive: false })`, not React props, because React's passive touch listeners can't stop Safari's gestures, which ate the start of Pencil strokes. The first contact draws a dot; strokes live in refs, each segment is drawn directly, and `onStroke` (selecting the box for 消す) fires only on pen-up, so nothing re-renders mid-stroke), `LetterBoxes.jsx` (the boxes + 消す / 戻す; `locked` after answering), `HandwritingInput.jsx` (the review's answer area, see below), `HwTestPage.jsx`, `HwTestRoot.jsx`. Also `writtenAnswer()` (what is written: `card.en` without optional `( )` / `[ ]` words; typing's `checkSpelling` accepts it as exact) and `readText()` in `answerLayout.js`, `readBoxes()` in `checkAnswer.js`. Tests: `answerLayout.test.js` (incl. `fitsBoxes`), `checkAnswer.test.js` (incl. `bestMatch`), `batch.test.js`, `HandwritingInput.test.jsx`, `model.test.js` (runs the real model and `preprocessLetter` in Node against the Python reference data).
- 手書き in reviews (`StudySession.jsx`, no separate flow: the same cards as typing mode, the same `typedResult` / `send()` / わからない / 次へ / まだ・わかった handling):
  - When a review starts in 手書き mode with any Japanese → English card, `loadModel()` starts at once (TF.js import, model, then the background warm-up), so the first card doesn't wait. If it fails (or a read fails later), `handwritingFailed` switches that session to typing with `handwriting.unavailable` (手書きの準備ができませんでした。今回はタイピングで答えてください。) above the typing box.
  - `HandwritingInput` replaces the typing box: hint Apple Pencil で、1マスに1文字ずつ書いてください, the boxes (pen only, never the finger/mouse option), 消す / 戻す, わからない and こたえる (disabled until something is written; 読み取り中… while reading). After answering the boxes stay (locked, colored by score), then 次へ (`TypingArea` phase next) or まだ / わかった (`AnswerArea`).
  - All boxes correct or lenient → like an exact spelling: `got_it` sent at once with the **target word** (`writtenAnswer(card.en)`) as `p_typed`, never the letters read (e.g. "flsh" for "fish"), so `record_answer` gives the spelling bonus; ✓ 正解！, "+1 スペル", Lv float. Lenient boxes are orange with one 「x」が「y」に見えるかも。気をつけて書こう！ line per pair. With `LENIENT_GIVES_BONUS = false`, a word with a lenient box is still `got_it` but sent without typed text (no bonus).
  - Alternate answers: boxes always come from the main english. An alternate is also accepted when it fits the same boxes exactly (`fitsBoxes()` / `fittingAlternates()` in `answerLayout.js`: same letters per word, spaces and printed characters in the same places, curly = straight apostrophes); others can't be written. `bestMatch()` in `checkAnswer.js` scores the boxes against the main answer, then each fitting alternate (same lenient rules), and the main answer wins if it passes, else the passing alternate with the fewest lenient boxes. An accepted alternate is sent as `p_typed` (so the database gives the bonus) and shows the same 教科書の答え line.
  - Any box wrong → 読み取り: the letters read (? = empty box), wrong ones in `danger`, lenient ones orange, plus 正しい答え; then まだ / わかった, sent with the read text as `p_typed` (as typing mode sends what was typed).
  - `answer_log` has no answer-mode column; recording `handwriting` would need SQL, so propose it rather than adding it.

## How to work with me
- Make small, focused changes. Before large refactors (like reorganizing folders or moving logic between many files), propose a plan and wait for approval.
- After a change, run `npm test`, `npm run lint` and `npm run build`, then summarize in a few plain sentences what changed and how I can test it.
- If you are not certain a step or command is correct, say so instead of guessing.
- Work on a branch, not on `main`. Suggest a git commit message after each working change.
- Never push to `main` (or merge into it) unless I say so, because that deploys to students. Don't push other branches unless I ask.
